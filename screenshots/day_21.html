01 / Core Concepts: RBAC, Pod Security & Debugging Workflow

Section 01 / Concepts

Security & Authorization Mechanisms

  • ServiceAccount: Identity used by pods, applications, or automation tools to authenticate to the API server.
  • Role & RoleBinding: Namespaced permissions and bindings. Deny-by-default; grant only required verbs.
  • Pod Security Standards: Privileged, Baseline, and Restricted profiles. Restricted is the strongest profile.
  • Hardened SecurityContext: Enforces runAsNonRoot: true, readOnlyRootFilesystem: true, and capability drops.
  • Debug Order: get → describe → logs → events → exec. Always inspect status and Events first.

Essential kubectl Commands for Day 21

  • kubectl auth can-i ... --as-system:... — Verify effective RBAC permissions.
  • kubectl label namespace secure ... — Enforce Pod Security Standards on a namespace.
  • kubectl describe pod <pod-name> -n lab — Inspect scheduling failures and probe events.
  • kubectl logs <pod-name> -n lab --previous — Retrieve crash logs from exited containers.
  • kubectl set image deployment/... — Update container image tags to resolve pull errors.
  • kubectl delete namespace secure lab — Clean up lab resources after verification.

10 / Interview Readiness & Architecture Q&A

Section 10 / Interview Q&A

1. What is RBAC and how do you verify it?

  • Controls who can perform actions on resources within a scope. Verified using kubectl auth can-i.

2. Why avoid running containers as root?

  • Non-root execution significantly limits the blast radius of a compromised or vulnerable application.

3. What are Pod Security Standards?

  • Profiles named Privileged, Baseline, and Restricted that enforce security best practices at the namespace level.

4. What is the standard debugging order?

  • get → describe → logs → events → exec. Always inspect status and Events before modifying configurations.
